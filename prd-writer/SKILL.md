# PRD Writer · 需求文档

来自订阅产品付费墙与默认套餐迭代。

## 先读这个

1. **PRD 的标准不是"写完"，是研发能实现、测试能验收、上线能对账。**
2. **数值必须可实现**：给公式 + 逐级数表；禁止"适当增加""视情况而定"。
3. **每个参数三件套**：默认值 ｜ 是否进远程配置 ｜ 生效层级（全局/角色/用户）。
4. **指标必须指得到埋点**，每个埋点事件要能回答"谁用它做什么决策"。
5. **待定项不悬空**：行内 🔵 标记 + 集中汇总，拍板后回填并删除标记。

## 一、先判断写哪种骨架

### A. 功能模块型

每个模块固定六项：

| 项 | 内容要求 |
|---|---|
| 需求名称 | 一句话说清模块是什么，括号内给关键机制速览 |
| 业务流程 | 箭头串起主路径 + 旁路，标注依赖服务（= 待后端定义） |
| 原型图 | 留位，链接或截图 |
| 界面交互说明 | 逐元素编号 ①②③：文案、交互、数据来源、空值兜底，一个元素不落 |
| 数据埋点 | pv、uv 逐条列，每条埋点标注它喂给哪个指标 |
| 特殊场景 | 异常与降级逐条编号：弱网、超时、素材缺失、服务异常、防刷 |

### B. 规格定义型（数值体系 / 经济系统 / 接口口径）

概述与设计原则 → 名词与口径定义 → 规格主体（计分表 / 曲线表 / 联动规则）→ 防刷与边界 → 展示与可见性 → 数据规格（事件字段、远程配置清单、埋点补充）→ 调参与迭代机制 → 待拍板项 → 附录。

两种可以混合：规格型 PRD 里的交互场景，按 A 的六项展开。

## 二、写作纪律

- **数值给公式 + 逐级数表**。例：`XP(n) = 10 × n²`，附 L1–L10 每级数字。
- **口径词必须可执行**。例：误触 = 面板唤起后 <1s 收起且无后续动作；首次 = 该设备首次完成支付，而不是首次打开。
- **指标 ↔ 埋点逐条对账**；埋点公共属性（user_id、session_id、来源渠道等）要声明。
- **异常与降级必写**：弱网、超时、素材缺失、服务异常、防刷；写清降级后的用户体验，不能只写"报错提示"。
- **待定项**：行内 🔵 + 汇总表（内容 / 建议方案 / 决策人 / 影响模块 / 截止）。
- **写作红线**：结论不说满、判断带依据、引用带可点链接、去术语、括号内不拆行、中文引号统一用 ""。
- **对外称呼**：文档内出现团队成员一律用昵称，不写全名。

## 三、交付前自检

- [ ] 每个数值有公式或逐级数表，无"适当/酌情"字样
- [ ] 每个参数带三件套（默认值 / 远程配置 / 生效层级）
- [ ] 行内 🔵 与"待拍板项"一一对应，无悬空
- [ ] 指标 ↔ 埋点逐条对得上；公共属性已声明
- [ ] 每个模块有异常与降级场景
- [ ] 口径词（首次 / 会话 / 误触 / 有效互动）都有可执行定义
- [ ] 标题带版本号；引用链接可点；待定项标记已清理
- [ ] 修订记录已更新

## 四、版本与评审闭环

- 初稿 v1.0 → 评审 → 结论回填后加"（评审后）"或升 v1.1，由用户定。
- 文档末尾固定"修订记录"：日期 ｜ 版本 ｜ 改了什么 ｜ 依据（评审/会议/数据）。
- 评审回填保留修正痕迹（原表述 + 修正标注），不抹掉重写。
- 用户手改过的文档只做增量修改，禁止清空重建。
